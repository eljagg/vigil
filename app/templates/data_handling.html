Data handling

Version {{ version }} · How Vigil handles your data, and how to verify it

This page exists for operators, security reviewers, and auditors who need to understand exactly what Vigil reads, what it does not read, and how to verify each claim independently. Every claim on this page is designed to be checkable without taking our word for it.

Summary in plain language

What Vigil reads Three fields per file, and only these three:
  • Filename — e.g. backup_2026-04-29.bak_encrypted
  • Size in bytes — e.g. 9500000000
  • Last-modified timestamp — e.g. 2026-04-29T02:30:00Z
What Vigil does NOT read
  • File contents — Vigil never opens the actual bytes of any file.
  • File ownership, permissions, or extended attributes.
  • Encrypted file payloads — the _encrypted in a filename is checked as a string suffix only; Vigil never attempts to decrypt anything.
What Vigil does NOT do
  • Copy files anywhere.
  • Upload files to any server.
  • Download files from any source.
  • Modify files on disk in any way (Vigil only requests read permission, not write).
  • Send data to any third party. The only network destination is the Vigil server itself.

Where data goes

When an operator runs a scan, the browser walks the chosen folder and builds an in-memory list of {filename, size_bytes, mtime} records — one per file. This list is serialized as JSON and posted in a single HTTP request to the Vigil server's /api/scan/submit endpoint. The server stores the manifest in its Postgres database and computes the diff against the previous scan of the same folder.

No file content is ever transmitted. No file content is ever stored. There is no caching layer. There is no "raw upload" path.

How to verify these claims

These claims are not asking for trust. Each one can be verified independently using one of the methods below.

Verification method 1 — Inspect the network traffic

This is the strongest single piece of evidence and takes about 30 seconds.

  1. Open Vigil in Chrome (or any Chromium browser).
  2. Press F12 to open DevTools.
  3. Click the Network tab.
  4. Tick Preserve log so requests aren't cleared on navigation.
  5. In Vigil, run a scan against any folder.
  6. In the Network tab, find the POST /api/scan/submit request.
  7. Click it, then the Payload tab to see exactly what was sent.

You will see a JSON body containing only the three fields per file. No base64 blobs. No binary data. No file contents in any form. The total payload size is small even for very large folders — a 1 GB backup folder produces only tens of kilobytes of metadata.

Verification method 2 — Read the source code

Vigil is open by design. The code that walks the folder and builds the manifest is in app/static/js/scanner.js, in a function named walkDirectory. The relevant section is roughly 40 lines of plain JavaScript. The reviewer should look for the calls below.

What you will find:

  • entry.getFile() — returns a File object describing the file.
  • file.size — reads the size attribute (a number).
  • file.lastModified — reads the timestamp attribute (a number).
  • file.name — reads the filename (a string).

What you will NOT find anywhere in the codebase:

  • file.text() — would read file contents as a string.
  • file.arrayBuffer() — would read file contents as bytes.
  • file.stream() — would read file contents as a stream.
  • FileReader — alternative API for reading file contents.

These four are the only ways a browser can read file contents. None of them appear in Vigil's source. A reviewer can confirm this with a simple text search.

Verification method 3 — Inspect the database schema

Even if the browser somehow sent file contents, the Vigil server has nowhere to store them. The database schema for file records is defined in app/models.py as the FileSnapshot class, with columns:

  • relative_path (text) — path inside the scanned folder
  • filename (text) — the file's name
  • size_bytes (integer) — the size
  • mtime (timestamp) — the modification time
  • is_encrypted_named (boolean) — derived from the filename suffix
  • prev_size_bytes, size_delta_bytes, is_new — diff fields, all derived from sizes

There is no column to store file content in any form. The receiving API endpoint (app/routes_api.py) ignores any extra fields a client might send.

Verification method 4 — Audit the network policy

Vigil's container is configured to only accept inbound traffic on its HTTPS port. There is no outbound connection initiated by Vigil to any third-party service for scan data. The only outbound connection Vigil may make is to a configured email backend (SMTP relay or Resend API) when sending weekly reminders — and those emails contain no file data, only the names and counts of scanned paths.

Permissions Vigil requests

When an operator clicks Browse, Chrome shows a dialog like: "Allow this site to view and copy files?"

This wording is set by Chrome and applies to any site that uses the File System Access API. It describes the maximum capability the API could grant — not what Vigil actually does with that capability. Vigil requests read-only permission. It does not request write permission. The "copy" word in Chrome's dialog refers to JavaScript's ability to copy file contents into the browser tab's memory — which Vigil does not do, as documented above.

Data retention

Vigil retains scan manifests indefinitely by default — they are part of the audit trail. Administrators can hide individual scans (which removes them from operator views but preserves them in the database for audit). The data retained per scan is the same metadata described above: filenames, sizes, timestamps. No file content.

Self-host considerations

Vigil is designed to be self-hosted inside your own infrastructure. When deployed inside your network, file metadata never leaves your control. The only third-party touchpoint (in default configuration) is the email delivery backend, if configured.

Questions

This page is intended to give security reviewers a complete picture without needing to ask. If a question isn't answered here, please contact your Vigil administrator or the project author directly.
